# Route Planning Data

This directory contains generated, routing-facing indexes over the source CSVs and Phase 2 constraint tables.

The source tables remain canonical. These files are a workbench for asking route-planning questions without repeatedly hand-joining objectives, support tables, location geography, and Markdown constraint tables.

## Files

| File | Purpose |
| --- | --- |
| `objective-route-index.csv` | One row per objective, with routing classification fields, location/geography joins, support-table candidate summaries, and constraint summaries. |
| `objective-constraints.csv` | One row per objective per referenced Phase 2 constraint-table row. |
| `*.template.csv` | Header templates used by `tools/validate_route_planning.py`. |
| `route-planning.sqlite` | Optional local SQLite workbench generated by `tools/build_route_planning_database.py`; ignored by git. |

## Regeneration

Run:

```bash
python3 tools/build_route_planning_index.py
python3 tools/build_route_planning_database.py
python3 tools/validate_route_planning.py
```

`objective-route-index.csv` and `objective-constraints.csv` are committed because they are reviewable route-planning artifacts. The SQLite database is generated output only.

## SQL Usage

The SQLite workbench loads all project CSVs as text tables and adds route-oriented views:

| View | Use |
| --- | --- |
| `route_objective_workbench` | Main objective workbench with objective prose fields joined back onto the generated index. |
| `route_unclassified_objectives` | TB-022 queue for objectives whose placement or rigidity remains unclassified. |
| `route_hard_constraint_queue` | Constraint rows whose severity implies a hard gate, hard save, branch, or route warning. |
| `route_location_objectives_by_corridor` | Geography-sensitive objective rows grouped by route cluster/corridor. |
| `route_candidate_selection_queue` | Objectives with multiple support candidates or multiple geography points. |

Example:

```sql
SELECT objective_id, objective_name, primary_route_corridor, constraint_types
FROM route_objective_workbench
WHERE route_index_status = 'needs_classification'
  AND primary_route_cluster = 'northern_skyrim'
ORDER BY primary_route_corridor, objective_name;
```

## Operating Contract for Later Agents

Use this directory as the routing workbench, not as a new source of gameplay facts.

The canonical data remains:

| Canonical source | Use |
| --- | --- |
| `data/objectives/objectives.csv` | Objective identity, category, current route placement, current routing rigidity, and source-note citations. |
| `data/constraints/*.md` | Source-backed routing laws and exact human-reviewed constraint wording. |
| `data/locations/location-geography.csv` | Hub/corridor geography support for route clustering and Survival Mode planning. |
| Domain support tables under `data/books/`, `data/items/`, `data/properties/`, `data/npc/`, and `data/skills/` | Candidate rows and domain-specific details for later selection/default passes. |

The generated files here answer "where should I look next?" They do not replace inspecting the canonical row before making a route decision.

## Standard Workflow

For TB-022 and later route-placement tasks:

1. Start from `objective-route-index.csv` or the SQL view `route_objective_workbench`.
2. Filter to the relevant task queue: unclassified objectives, hard constraints, geography/corridor group, branch candidates, or candidate-selection rows.
3. For any row with `constraint_count > 0`, inspect matching rows in `objective-constraints.csv`.
4. Before changing route placement, routing rigidity, warnings, or route prose, open the source file listed in `constraint_source_files` or `constraint_source_file`.
5. Edit the canonical target file, usually `data/objectives/objectives.csv` or a later route prototype.
6. Regenerate the index:

```bash
python3 tools/build_route_planning_index.py
python3 tools/build_route_planning_database.py
python3 tools/validate_all.py
git diff --check
```

Do not hand-edit `objective-route-index.csv` or `objective-constraints.csv`; regenerate them from canonical inputs.

## Column Semantics

Important `objective-route-index.csv` fields:

| Field | Meaning | Caution |
| --- | --- | --- |
| `route_index_status` | Generated triage status for routing work. | Use as a queue filter, not as a final classification. |
| `constraint_count` / `constraint_types` / `constraint_severities` | Count and summary of constraint rows linked to the objective. | Inspect `objective-constraints.csv` and the source constraint table before relying on the summary. |
| `primary_route_cluster` / `primary_route_corridor` | First geography row's generated cluster/corridor. | Good for coarse grouping; validate roads, passes, water, portals, and quest-state access before route prose. |
| `primary_nearest_*` fields | Nearest service/base support points from the geography layer. | Straight-line support only; not proof of practical pathing. |
| `support_table_refs` / `support_record_count` / `support_locations` | Candidate/support rows linked to this objective. | Multiple candidates require route selection later; the index does not choose the best one. |
| `candidate_status` | Whether the objective has none, one, or multiple support/geography candidates. | Candidate selection belongs to later route/default passes. |

Important `objective-constraints.csv` fields:

| Field | Meaning | Caution |
| --- | --- | --- |
| `constraint_type` | Generated broad class such as `leveled_reward`, `cell_entry_lock`, `quest_conflict_or_branch`, `trophy_dependency`, or `survival_constraint`. | Derived from source file, not a hand-reviewed new claim. |
| `severity` | Generated triage level: `hard_gate`, `branch_or_hard_save`, `warning`, `planning`, or `review`. | Conservative queueing only; source text decides final treatment. |
| `routing_rule` | Extracted route-relevant cells from the Markdown table. | May be terse or overinclusive; inspect the source row. |
| `hard_save_name` | Extracted hard-save label when present. | Only meaningful after branch/warning placement confirms timing. |
| `route_phase_owner` | Later phase most likely to consume the constraint. | Coordination hint only. |

## Task-Oriented Entry Points

Use these query surfaces by phase:

| Phase/task | Start here | Typical next step |
| --- | --- | --- |
| TB-022 routing rigidity | `route_unclassified_objectives`, then `objective_constraints` | Classify objectives in `data/objectives/objectives.csv`; regenerate indexes. |
| TB-023/TB-024 anchors and level skeleton | `route_hard_constraint_queue` and level-gated rows in `route_objective_workbench` | Identify fixed/late anchors; do not write detailed route prose yet. |
| TB-025 Survival geography | `route_location_objectives_by_corridor` | Group by cluster/corridor, then validate access model/cold/barrier flags against geography notes. |
| TB-026 flexible insertion | `route_candidate_selection_queue` plus corridor views | Pick safe nearby objectives only after constraints and candidate rows are checked. |
| TB-027 skill/perk/crafting | `route_objective_workbench` filtered by `category IN ('skill_perk','crafting_unlock')` and progression constraints | Use skill support tables and TB-020 notes for actual progression choices. |
| TB-028/TB-029 branches | `objective_constraints` filtered to `constraint_type = 'quest_conflict_or_branch'` | Build branch/default matrix from canonical conflict rows. |
| TB-030 checklist mapping | `route_objective_workbench` plus `data/checklist-mapping/coverage-matrix.csv` | Map stable route placements; checklist input is still required. |
| TB-032/TB-033 warning/validation | `route_hard_constraint_queue` | Place concise warnings, then validate route against source constraint tables. |

## Useful SQL Queries

Rebuild the database first if source CSVs changed:

```bash
python3 tools/build_route_planning_database.py
```

Unclassified objective queue for TB-022:

```sql
SELECT objective_id, objective_name, category, route_placement, routing_rigidity,
       constraint_types, candidate_status
FROM route_unclassified_objectives
ORDER BY category, objective_id;
```

Hard gates and hard-save candidates:

```sql
SELECT objective_id, objective_name, constraint_type, severity,
       constraint_source_file, source_section, row_label, hard_save_name
FROM route_hard_constraint_queue
ORDER BY severity, constraint_type, objective_id;
```

All constraints for one objective:

```sql
SELECT constraint_type, severity, constraint_source_file, source_section,
       row_label, routing_rule, source_notes
FROM objective_constraints
WHERE objective_id = 'OBJ-001750';
```

Geography grouping for Survival Mode planning:

```sql
SELECT primary_route_cluster, primary_route_corridor,
       primary_nearest_corridor_hub, primary_cold_risk,
       COUNT(*) AS objective_count
FROM route_location_objectives_by_corridor
GROUP BY primary_route_cluster, primary_route_corridor,
         primary_nearest_corridor_hub, primary_cold_risk
ORDER BY primary_route_cluster, primary_route_corridor;
```

Candidate-selection queue:

```sql
SELECT objective_id, objective_name, category, support_table_refs,
       support_record_count, support_locations
FROM route_candidate_selection_queue
ORDER BY category, objective_id;
```

## Do Not Treat These as Facts

Generated summaries can be stale or lossy if canonical files change or a Markdown table has unusual wording. In particular:

* `severity` is a triage hint, not a final risk judgment.
* `primary_*` geography fields are first-row support fields, not an optimized route choice.
* `support_locations` may summarize many candidates and truncate long lists.
* SQL tables load CSV values as text, so numeric comparisons need casts.
* The SQLite database is ignored generated output; rebuild it whenever the CSVs change.
